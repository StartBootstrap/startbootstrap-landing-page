Accessibility audit — Landing Page

"Start Bootstrap – Landing Page" theme · page dist/index.html

Standard: WCAG 2.2 level AA Date: June 6, 2026 Method: axe-core scan + manual code review + contrast tests Scope: home page (desktop + mobile)

1. Summary

The page is built on Bootstrap 5, which provides a decent baseline (semantic section HTML, visible focus by default, zoom allowed, responsive structure). The audit nonetheless finds 14 issues, several of which genuinely block screen-reader and keyboard users. The most critical ones concern form fields without labels and social icon links with no accessible name.

4. Detailed findings by principle

Perceivable

① Email fields without a programmatic label

WCAG 1.3.1WCAG 3.3.2WCAG 4.1.2Critical

The two fields #emailAddress and #emailAddressBelow have no associated <label>: they rely solely on the placeholder attribute. No <label> exists anywhere on the page. To a screen reader the field is announced "edit text, blank" with no indication of what to enter; moreover the placeholder disappears as soon as the user starts typing, which penalizes everyone.

⑧ Non-meaningful alt text on testimonials

WCAG 1.1.1Minor

The three portraits use alt="...". A screen reader literally reads out "dot dot dot". Since these images are illustrative (the name is already in text right next to them), they should carry an empty alt="" (decorative) — or descriptive text if they are deemed informative.

⑨ Decorative icons not hidden

WCAG 1.1.1Best practiceMinor

The feature-grid icons (bi-window, bi-layers, bi-terminal) are purely decorative <i> elements. They should carry aria-hidden="true" so they don't add noise for assistive technology.

⑬ White text over a background image (masthead)

WCAG 1.4.3Minor

The heading and form are white over a photo, with a semi-transparent dark overlay (opacity:0.5). The observed result is readable, but the contrast depends on the photo: replacing the image with a lighter one would fail the criterion. Recommendation: ensure a sufficiently opaque overlay or gradient to guarantee ≥ 4.5:1 regardless of the image.

Operable

② Social icon links with no accessible name

WCAG 2.4.4WCAG 4.1.2Critical

The three social links in the footer contain only an icon (<a><i class="bi-facebook"></i></a>), with no text and no aria-label. Confirmed by axe-core (link-name rule, "serious" impact): these links are announced as "link" with no destination. A screen-reader user cannot tell where they lead.

⑤ No skip link

WCAG 2.4.1Major

No "skip to content" link is offered at the top of the page. Combined with the missing <main> (issue ④), keyboard users must tab through the navigation on every load with no way to bypass it.

⑦ "Submit" button fake-disabled

WCAG 4.1.2WCAG 1.4.3Major

The button carries the .disabled class but not the disabled attribute nor aria-disabled. On a <button>, the Bootstrap class does not prevent keyboard activation: the perceived state (greyed out, opacity:.65) does not match the actual state exposed to assistive technology. The reduced opacity also drops the label's contrast below the 4.5:1 threshold.

⑪ Placeholder links href="#!"

WCAG 2.4.4Minor

The navbar brand, the footer links (About, Contact, Terms of Use, Privacy Policy) and the social links all point to #!, a non-existent anchor. These links are focusable but lead nowhere: they mislead the user and blur the link's purpose. Fill in real destinations (or remove them).

Understandable

⑥ Broken heading hierarchy

WCAG 1.3.1Major

Heading levels jump: after the masthead h1, the feature grid uses h3 (the h2 level is skipped); further down, the testimonials go from a section h2 to h5. Confirmed by axe-core (heading-order). Navigating by headings, heavily used with screen readers, becomes illogical.

⑫ Fragile error messages

WCAG 3.3.1Minor

Input error identification relies entirely on the external SB Forms script (data-sb-validations). Without an active API token, or if the script fails to load, no message appears. The .invalid-feedback blocks in text-white are also only legible on a dark background. Provide native HTML validation (required, type="email") as a baseline, independent of the script.

Robust

⑩ Duplicate identifiers

WCAG 4.1.1 (removed in 2.2)Minor

The ids submitButton, submitSuccessMessage and submitErrorMessage exist twice (masthead + call to action). Even though 4.1.1 no longer applies in WCAG 2.2, unique ids remain essential for reliable label/for associations, ARIA references and script targeting.

9. Priority fixes

  • First (critical): associate a <label> with each email field (①) and give each social link an aria-label (②). These two fixes unblock screen-reader use.
  • Next (major): wrap the content in <main> + add a skip link (④, ⑤); fix the heading hierarchy (⑥); raise the footer contrast (③); correctly expose the button's disabled state (⑦).
  • Finally (minor): meaningful alt (⑧), aria-hidden on decorative icons (⑨), unique ids (⑩), real link destinations (⑪), native fallback validation (⑫), guaranteed contrast overlay (⑬), metadata (⑭).

The technical detail of the fixes (source file, before/after snippet in Pug, SCSS and ARIA) is in the companion document plan-corrections.md.
